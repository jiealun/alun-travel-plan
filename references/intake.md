# intake.md · 需求澄清、候选目的地与研究后对齐

读这份文件的时机：S1 需求澄清、S2 选目的地、S4 研究后对齐。

## 1. 入口识别（S0 末尾）

先分清用户是哪一种，再决定问什么：

| 入口 | 信号 | 下一步 |
| --- | --- | --- |
| 选目的地 | "不知道去哪""周末有空""几天假" | S1 只问方向性信息 → S2 候选 |
| 做攻略 | 已有目的地、日期 | S1 补齐必要项 → S3 |
| 修改 | "把第二天改一下""预算加到 X" | 读现有 `trip.json` → 影响范围 → 局部更新（`delivery.md` §7） |
| 恢复 / 出发前复核 | "上次那份""出发前再帮我看看" | 找存档；找不到就请用户重新提供文件，⛔ 不假装记得 |

用户已经给出的信息一律沿用，不重新欢迎、不重复问卷（T02）。

## 2. 需求档案：八组信息

每个字段保留 **值、来源、状态**。状态四档：`user_stated`（用户明确）/ `extracted_pending`（从资料提取待确认）/ `default_suggested`（系统建议默认）/ `unknown`。写入 `request.field_status`。

| 信息组 | 需要明确的内容 | 处理原则 |
| --- | --- | --- |
| 出发与返回 | 出发城市或区域；最早离开、最晚返回时间；是否需要当天返家 | ⛔ 不默认用设备所在地；不要求精确家庭住址 |
| 日期与天数 | 具体日期、可否调整、过夜数、跨时区情况 | 相对日期（"下周末""十一"）转成绝对日期后**复述确认**；日期未定可先做按天模板 |
| 同行人员 | 人数、儿童年龄段、长者或行动便利性要求 | 只问影响安排的信息；⛔ 不索取证件或无关健康信息 |
| 预算 | 总额或人均、币种、包含项目、已付金额、弹性 | 住宿按房还是按人头、交通能否分摊必须明确 |
| 旅行节奏 | 早起接受度、每日活动长度、步行强度、休息需要 | "轻松"要转成能讨论的约束（几点出门、走多久要歇），不自动等同于固定步数 |
| 兴趣与排除项 | 美食、自然、人文、拍照等；必去 / 可选 / 不去 | 让用户区分**必须满足**与**尽量满足**；不用热门程度代替偏好 |
| 已定安排 | 车票、航班、住宿、预约时段、会面等 | 标 `confirmed / pending_payment / intent`；锁定项未经允许不动 |
| 交通与其他要求 | 自驾或公共交通、行李、饮食、无障碍、宠物等 | 按实际场景追问；不假定能开车、能爬楼、能吃某类食物 |

### 2.1 预算口径先说清

- **总旅行成本**包含已付部分；**"接下来还要准备多少钱"**只算未付部分。两者都要在交付里分开展示。
- 缺失价格是 `unknown`，不是 0。预算汇总给"低—高"范围，并单列未知项。
- 跨币种保留原币，注明换算汇率日期，或明确"暂不换算"。
- 儿童票、房间分摊、已付费用混在一起时（T16），按计价单位逐项拆开再合计。

### 2.2 系统默认不是用户要求

系统可以建议"非必要不换酒店""每天留机动时间""同片区优先"，这些记为 `default_suggested`，写在 `itinerary.assumptions` 里，⛔ 不能记成用户亲口要求。用户明确反对时可以调整，但不能用用户偏好覆盖安全、事实或时间可行性。

## 3. 用户资料的入口

问一句：有没有参考链接、笔记、截图、文件、预订信息或朋友推荐？

- 能读到的内容才纳入证据（`sources[]` 里 `source_type = user_material`）。链接打不开、图片看不清、视频正文拿不到 → 说明实际可见范围，⛔ 不假装读完。
- 用户资料分两类分开处理：**偏好**（"我想去这里"）与**事实**（票价、开放规则）。旧攻略保留玩法灵感，但其中的票价和开放规则要重新核实。
- 截图显示的预订 ≠ 当前仍有效或已完成支付；记为 `extracted_pending`，请用户确认状态。

## 4. 未确定目的地时的独立流程（S2）

1. **粗筛**：根据出发地、可用时间、预算、偏好排除明显不合适的方向（往返占掉一半以上时间、预算明显不够、与排除项冲突）。
2. **给 3—5 个候选**。候选不必都是城市，可以是玩法类型："同城轻松一日游""附近自然休闲""邻城两日人文游"。优先让候选**有真实差异**，⛔ 不给五个近乎一样的热门地点。
3. **每个候选说明六件事**：匹配理由、往返时间范围、**扣除交通后的实际可玩时间**、预算范围、主要缺点、关键不确定性。
4. **比较用有解释的维度**（"更适合少折腾""更适合看自然""带孩子更省心"），⛔ 不输出貌似客观的精确总分。
5. **保留用户选择**。用户明确说"你帮我定"时可以代选，但要写出所用假设，记入 `decisions[]`。
6. 用户未选定前只做必要的可行性调研（大交通是否可达、核心景点是否在开放期），⛔ 不为所有候选购买社媒资料或编排详细多日路线（T03）。

候选展示原型：

> **候选 A · 邻城两日人文游（例）**
> 匹配：你说想走走看看、不想太累，这里主要景点集中在老城区，步行可达。
> 往返：高铁单程约 1 小时（公开时刻表，未查余票）；实际可玩约 1.5 天。
> 预算：两人约 X—Y 元（住宿按房、不含购物；票价部分未核实）。
> 缺点：周末老城区人多。
> 不确定：其中一个博物馆需预约，放票规则待查。

## 5. 调研后何时再次询问（S4）

调研中发现以下任一情况，**集中沟通一次**，写进 `decisions[]`：

- 原预算不足；
- 必去地点关闭、或目标日期尚不能预约；
- 可玩时间明显少于预期（大交通比想象久、首末日被接驳吃掉）；
- 原定的轻松游会变成高强度步行；
- 加入某个新玩法会占用较长时段；
- 换住宿能显著改善路线；
- 已有安排之间冲突（T04）。

沟通格式固定为四段：**发现了什么 → 影响是什么 → 有哪些选择 → 建议及理由**。

正例：

> 查到 X 博物馆周二闭馆，而你的第二天正好是周二。
> 影响：第二天上午原本安排在这里的 2 小时要换。
> 选择：① 换到第三天上午（第三天下午的行程往后挪 1 小时，返程赶得上）；② 换成同片区的 Y 馆（不用预约，步行 10 分钟）；③ 去掉。
> 建议 ①，因为 X 是你的必去项目。

反例（⛔）："要不要安排 citywalk？"——没说要多少时间、替代什么。

必去项目与返程时间无法同时满足时：报告冲突并给选择，⛔ 不偷偷删必去项目，⛔ 不擅自延迟返程。

## 6. 不该问的

- 证件号码、完整身份信息、健康状况（只问"有没有需要照顾的行动便利性要求"这类影响安排的信息）。
- TikHub 令牌（在欢迎语里）。
- 已经回答过的问题。
- 没有实质取舍的确认（"这两个都在同一条街上，我先排 A 再排 B 可以吗"——直接排并解释即可）。
