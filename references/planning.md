# planning.md · 行程规划方法

读这份文件的时机：S5 排行程；S10 修改行程时重排某一天。

## 1. 方法：约束优先、片区分组、时间窗排程

借鉴带时间窗的路径规划思路（把地点、交通时间、允许到访时间一起考虑），但旅游还包含"哪些景点值得选"，不能照搬要求遍访所有节点的车辆路线模型。首版用**可解释的启发式**，不装求解器：先锁定约束 → 分片区和选点 → 排序、计算、修复。

数据精度不足时的正确反应是**增加余量、减少跨区**，而不是用复杂算法制造虚假的最优解。

## 2. 先分清硬约束、偏好和默认

| 类别 | 例子 | 处理 |
| --- | --- | --- |
| 硬约束 | 出发/返回边界、已预订时段、已知关闭、不可超预算、用户明确的行动限制 | 不能违反；违反即 `blocking` |
| 用户要求（必去 / 不去） | `request.interests.must` / `avoid` | 无法满足 → 报告冲突并请求取舍，⛔ 不悄悄删 |
| 偏好 | 轻松、拍照、美食、少换乘、不早起 | 尽量满足，说明取舍 |
| 建议默认 | 非必要不换酒店、每日留机动、同片区优先 | 写进 `assumptions`；用户明确反对可调，但不能用它覆盖安全、事实、时间可行性 |

优化顺序是**分层比较**，不是混成总分：① 没有硬约束冲突 → ② 尽量满足已确认的重要体验 → ③ 减少无意义的交通、换宿、成本和不确定性。每次较大取舍都能解释理由（写进 `itinerary.tradeoffs`）。

## 3. 八步规划流程

| 步骤 | 操作 | 产物 |
| --- | --- | --- |
| 1 锁定安排 | 固定大交通、已订住宿、预约、会面、返程边界 | 不可擅自修改的时间与位置锚点（`items[].locked = true`） |
| 2 过滤候选 | 排除已知不可去或明显不合适的地点；其余分必去 / 优先 / 可选 | 有证据与游览时长范围的候选池（`places[]`） |
| 3 片区分天 | 按相邻区域和交通走廊组合，同时考虑哪天开放 | 每日主题、片区、住宿基点（`days[].theme / region / lodging_base`） |
| 4 排时间窗 | 优先安排固定时段或开放限制强的项目 | 一天的骨架，不先塞满自由活动 |
| 5 插入体验 | 插入同片区可选点，保持可接受节奏 | 主要路线与删减优先级 |
| 6 补全生活时间 | 交通、用餐、休息、排队、寄存、进出站、机动 | 完整时间账本（`transit / meal / rest / buffer` 项） |
| 7 局部改善 | 比较交换顺序、移到另一天、减少跨区 | 更少折返且仍满足时间窗的路线 |
| 8 压力测试 | 用偏保守的交通和排队估计重算，检查替代分支 | 可行路线、风险、备用计划 |

⛔ 每次换顺序都要重新检查开放、预约和交通；地理顺序改善后，原有时间核查**不再自动有效**。
⛔ 不能靠无依据地压缩游览和休息时间让计算"刚好成立"。

## 4. 一天的时间计算规则

统一使用**带日期和时区**的时间（ISO 8601，如 `2026-10-10T09:30:00+08:00`）。跨午夜活动、跨时区交通不以简单钟点字符串相减（T06）。

```text
下一站抵达        >= 上一项结束 + 路段时间上界(time_max) + 转场余量
允许入场时间      >= max(抵达时间, 开始接待时间) + 计划排队时间
允许入场时间      <= 最后入场时间(last_entry)
活动结束          =  实际入场时间 + 计划游览时长
活动结束          <= 所选开放区间的结束时间
```

- 以上是保守排程示意；入场、排队、游览起点按场馆真实规则建模。
- 分上午/下午开放的场馆要选**完整可用**的区间；预约的入场时段 ≠ 全部游览时段。
- 活动与交通都进入同一时间线：`transit` 项与 `visit` 项一样有 `planned_start / planned_end`，避免"看起来没重叠，实际没留路上时间"。
- **机动比例**：初始按可自由安排时段的 15%—25% 留 `buffer`，按节奏、同行者、信息精度调整。这是待测的产品参数，不是经验定律，也不能代替机场或车站的实际要求。
- 首末日：往返住处/住宿区域、行李、安检/进站、接驳都要计时，不只算车程或飞行时长。

`validate_trip.py` 会检查：同一天内项目不重叠；有 `incoming_leg_id` 的项目，开始时间 ≥ 上一项结束 + `time_max`；项目落在 `opening_windows` 内、且不晚于 `last_entry`。

## 5. 预算、体力与住宿联合考虑

时间冲突按带时区的实际时刻比较，跨日活动也参与全程重叠检查；开放时间未知不能跳过预约失败和事实冲突核查。

**预算**至少覆盖：大交通、住宿、市内交通、门票、餐饮、机动。每类分 `paid`（已付）、`min / max`（预计未付范围）、`status`（known / estimate / unknown）。

- 按明确计价单位汇总（房 / 人 / 次），展示低—高范围。
- 预算上界超过硬限制 → 优先删减可选项目或请求调整，⛔ 不隐藏缺项。
- `unknown` 类别单独列出并计入“预算是否成立”的判断（未知不是零）。有未知费用时只能说“已知费用未超限，尚不能确认”；人均预算须先确认 budget_persons 才能换算全队上限，外币未换算时保留条件提醒。分类金额统一为全队口径，已付合计与用户已付金额交叉核对。

**体力**结合连续步行、上下坡、楼梯、天气暴露、休息间隔判断，给 `days[].intensity`（light / moderate / heavy）。没有数据不编造精确步数；对同行者的要求只用用户明确约束，⛔ 不自动做健康判断。

**住宿**默认推荐 2—3 个区域（`lodging.regions[]`），每个说明交通便利性、适合的日程、预算参考、缺点，不强求具体酒店。未定住宿时把区域代表点或范围标为规划假设；用户订好后再按实际位置更新路段。

**换住宿**的收益要扣除退房、寄存、携行李、跨区交通、再次入住的成本。确有明显改善 → 先提出比较，用户确认后再排（决策关口）；⛔ 不能只为缩短地图上一段路就换酒店。

**大交通**（`transport_major[]`）区分 `booked / to_book / suggested`；公开搜索只能取得路线建议或价格参考时，⛔ 不声称有余票或可按该价购买。真实到达站、航站楼、出发时刻、进出城时间都要确认。

## 6. 替代方案必须也能执行

每天按实际风险准备必要的替代（雨天、预约失败、排队过长、体力不足）。替代也要检查开放、位置、时间、费用，⛔ 不能只列一个景点名。

`Alternative` 四要素：

| 字段 | 内容 |
| --- | --- |
| `trigger` | 触发条件（"X 馆预约失败""当天降雨概率高""上午结束时已超过 14:00"） |
| `replaces_item_ids` | 替换哪一段 |
| `rejoin_at_item_id` | 从哪里接回原路线 |
| `cost_delta` / `time_delta` | 费用与时间变化 |

- `instant = true`（即时备用）只能给**无需预约、随时可切换**的活动；同样要抢票的备选必须 `instant = false` 并写明自己的前置条件（`requires_booking = true`）。
- 替代方案自身也有 `verification_status`。

## 7. 每日活动不只是地点名

`items[].description` 至少回答四件事：**为什么安排这里、主要看什么、预计怎么游览、为什么与前后顺路**。餐饮可推荐就餐片区和选择标准；特定餐馆仅在资料支持时推荐，不保证排队或座位。

时间显示为当地日期与时间。对估算项目，排程时刻是规划结果，不代表交通或营业时间本身有分钟级精度，相关提示（`tips`）要邻近展示。

## 8. 排完一天的自检

- 每个 `visit` 都有 `place_id`、`fact_ids`（至少一条开放相关事实，哪怕状态是 unknown）、`booking_status`、`verification_status`。
- 相邻不同地点之间要么有 `transit` 项 + `incoming_leg_id`，要么明确写"同一场所内步行"。
- 必去项目都出现在某一天，或写进 `itinerary.unmet` 并已与用户沟通。
- 首末日与大交通、住宿衔接有余量。
- 每天至少一个替代关系，或写明"当天无高风险项，不设替代"。
