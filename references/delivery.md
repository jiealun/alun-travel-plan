# delivery.md · 方案确认、MD、HTML、1:5 长图、存档与修改

读这份文件的时机：S7 方案确认、S9 最终交付、S10 修改与恢复；展示风格选择图或制作长图时另读 `references/long-image.md`。

## 1. 同一数据源，三个表达层

- `travel-plan/<trip_id>/trip.json` 是唯一业务数据源，**叙述性内容（介绍、取舍解释、预约步骤、来源说明）也在里面**。
- MD 与 HTML 由 `scripts/render_outputs.py` 从同一 `plan_version` 渲染；1:5 长图从用户已确认的该版本抽取必要信息。
- ⛔ 不允许三个生成任务各自重新规划、补数字、改措辞。渲染脚本缺什么就显示"未知 / 待确认"。
- 每份产物带 `trip_id`、`plan_version`、`generated_at`、内容指纹（trip.json 规范化后的 SHA-256 前 12 位）。
- 固定署名「**由 Alun旅行规划生成**」来自 `assets/templates/attribution.json`（只读）：MD 文末、HTML 页脚、长图安全边距内。署名是渲染项也是验收项。

## 2. 方案确认与交付流程（S7、S9）

S6 核查完成后先向用户给出完整可阅读的方案预览：每日时段与顺序、已锁定安排、住宿和交通、预算、尚未落实的预约、风险和备用路线。明确询问是否确认这版方案；用户未明确确认或提出修改时，不进入选风格/长图阶段。确认后把未交付版 `trip.json` 的 `user_confirmed` 设为 `true`；若该版本已有不可变快照，须先升版本，不覆盖历史。再按 `references/long-image.md` 展示固定的一行四列风格选择图，并在用户选定风格后制作终稿。

命令以项目目录为工作目录。宿主先确认 Python 3 可用；Windows 示例使用 `python`，其他宿主可替换为实际解释器。安装成 Skill 后，脚本路径应解析到 Skill 所在目录，行程路径使用当前工作区的绝对路径。

```bash
# 1) 核查（无阻断才继续；有阻断先走 audit.md 的修复循环）
python scripts/validate_trip.py travel-plan/<trip_id>/trip.json
# 2) 同源渲染 MD + HTML + manifest
python scripts/render_outputs.py travel-plan/<trip_id>/trip.json
# 3) 产物检查：文件存在、指纹一致、署名在、覆盖率 100%、无凭据、无远程依赖
python scripts/validate_trip.py travel-plan/<trip_id>/trip.json --check-outputs
# 4) 已选风格的 PNG 完成且人工视觉核查后，核验尺寸并加入同版本 manifest
python scripts/register_long_image.py travel-plan/<trip_id>/trip.json travel-plan/<trip_id>/outputs/<trip_id>_v<N>_1x5.png
# 5) 再核对 MD、HTML、PNG 的版本与文件指纹
python scripts/validate_trip.py travel-plan/<trip_id>/trip.json --check-outputs
```

同版本文件已存在时拒绝覆盖；修改数据须先 `save` 升版本。`--force` 只允许从相同内容重新渲染，不能覆盖历史快照。渲染成功前会建立不可变快照，manifest 最后写入；失败不留下“已交付完成”的 manifest。所有写入前先做结构和凭据检查，渲染还会拒绝阻断问题。

产物检查会重新比较当前 `trip.json` 的完整指纹，并从 MD 和 HTML 可见正文重新核对业务内容；不能用旧 manifest 或 HTML 内嵌 JSON 代替可见内容。自定义 manifest 文件名须为 `manifest.*.json`，核查报告须为 `audit.*.json`，两者不能覆盖原数据或 `versions/`。覆盖检查不代替人工判断路线、事实和表达是否合理。

最终交付时对用户说清四件事：

1. 方案状态（探索草案 / 条件式 / 截至核查时可执行）和为什么；
2. 出发前必须做的事（清单里 `must` 项）与截止时间；
3. 哪些是估算、哪些没查到（路段、开放时间、价格）；
4. MD、HTML 与一张 1:5 PNG 长图在哪里、怎么打开（HTML 双击即可，不需要网络）。

⛔ 不说"已经帮你安排好一切"；⛔ 没跑脚本就不说"脚本校验已通过"。

## 3. 完整 MD 的信息结构

| 模块 | 必须包含 |
| --- | --- |
| 开篇总览 | 目的地、日期、人数、预算口径、节奏、方案状态、核查时间 |
| 规划依据 | 用户需求、锁定安排、采用的假设、重要取舍、未满足项目 |
| 行程总表 | 每天主题、区域、主要顺序、住宿基点、强度、主要提醒 |
| 每日详细行程 | 开始/结束时间、活动介绍、停留时长、交通方式和留时、费用、预约、注意事项、来源 |
| 住宿与大交通 | 推荐区域和理由、是否换宿、已定与待定交通、首末日衔接 |
| 预算 | 分类上下界、已付与未付、未知费用、预算是否成立 |
| 备用方案 | 触发条件、替换段、衔接方式、费用与时间影响 |
| 出发前清单 | 优先级、截止时间、用户动作、完成状态、确认入口、未解决怎么办 |
| 天气与准备 | 真实预报或季节参考的区别、获取不到的说明、装备建议 |
| 核查与资料 | 重要来源、核查日期、未解决问题、变更记录、固定署名 |

每日活动不只是地点名：至少解释**为什么安排这里、主要看什么、预计怎么游览、为什么与前后顺路**。餐饮推荐就餐片区和选择标准；特定餐馆仅在资料支持时推荐，不保证排队或座位。

时间显示为当地日期与时间。估算项目要邻近提示"排程时刻是规划结果，不代表交通或营业时间本身有分钟级精度"。

## 4. 单文件 HTML 的实现规则

模板：`assets/templates/itinerary.html`（v2「旅行手账」）。渲染器只做占位符替换，所有外部文本经 `html.escape`。

v2 的表达形式（都由 trip.json 里已有的数据驱动，不新增内容）：首屏「旅程海报」（渐变底 + 等高线纹理 + 出发→D1…Dn→返程的路线示意 SVG，路线描画动画、节点逐个弹出、四张信息票根、方案状态印章）；总览的信息瓦片、横滑天卡片、假设/取舍提示卡；每日行程的时间轴（时间列 + 图标节点 + 卡片，交通与机动为紧凑连接行，状态色条按核查状态变化，Plan B 卡片挂在当天末尾）；住宿区域卡、车票样式的大交通卡、预算的四个汇总数字 + 分类堆叠条（固定顺序的 6 色分类色板，经 dataviz 校验；已付用斜纹、未知用「?」段、上限用红线）+ 明细表；清单卡片带进度条与完成划线；风险、能力标签、折叠的事实/来源/决策、版本时间线。动效：滚动进入（IntersectionObserver）、按天切换淡入、悬停微抬、进度条过渡、回到顶部；全部在 `prefers-reduced-motion: reduce` 下关闭。

- **自包含**：正文、CSS、必要 JS 都在文件内；不引用 CDN、远程字体、远程脚本；页面打开后不调用 TikHub、天气或任何远程接口；外部来源与预约链接只在用户点击时打开（`rel="noopener noreferrer"`）。
- **不 fetch 旁边的 JSON**：`file://` 下同源策略与跨文件读取有限制，行程快照直接内嵌在 `<script type="application/json">` 里（`</` 已转义），只作数据读取，不执行。
- **渐进增强**：正文在生成时已写进 HTML；没有 JS 时全部日期与关键内容可见；脚本可用时再启用按天切换、"显示全部"、复制、勾选记忆。⛔ 不能先隐藏全部内容再等脚本显示。
- **五个固定区域**：旅行总览；日期导航与当天行程；住宿/交通/预算；出发前清单；证据、风险与版本信息。手机优先单列，桌面加侧栏目录。关键风险与状态提示放首屏，不藏在折叠区。
- **交互与无障碍**：按天按钮显示日期与星期，可键盘操作（`aria-pressed`）；状态不只靠颜色（有文字徽标）；打印时自动展开全部。
- **清单计数**：`na` 项标为“不适用”、不可勾选、不计入完成率；两处进度条与完成文字同步。
- **勾选记忆**：`file:` 页面下 `localStorage` 行为没有统一保证——只在可用时尝试记住勾选，失败不影响页面，并明示"本次勾选可能不会在关闭后保留"。浏览器不改写原 HTML，不宣称同步到其他设备。
- **复制按钮**失败时提示手动选择；权限问题不阻断使用。
- **图片**：在生成阶段完成下载、许可核对与压缩，作为 `data:` URI 内嵌；初始体积目标 8 MB 以内（待测的体验目标）。没有合适图片就用文字版，⛔ 不拿错误地点的图片凑数。首版渲染器不内嵌图片；需要时在模板中增加图片位并记录许可。
- **安全**：不用 `innerHTML` 拼接外部文本（模板 JS 只用 `createElement` / `textContent`）；只允许 `http(s)` 外链；不内嵌第三方 HTML 或远程脚本。

`validate_trip.py --check-outputs` 会拦：外部 `<script src>`、外部样式表、`fetch/XMLHttpRequest/sendBeacon`、缺署名、缺版本号、凭据模式。

## 5. 配图来源与许可

优先级：用户允许复用的图片 → 许可明确的开放素材 → 明确允许使用的官方图片。逐张记录原始页面、作者、许可、署名要求、用途。

- 图片来自官方页面 ≠ 可以自由转载。
- 小红书 API 返回图片地址 ≠ 转载许可；许可不清楚只保留来源链接，不下载嵌入。
- 禁止热链跟踪图片、任意远程脚本、原样嵌入第三方 HTML。
- 图片地点不符、下载失败、许可不清 → 不用（T18）。

## 6. 风格选择图与 1:5 长图（S8、S9）

按 `references/long-image.md` 执行两次独立确认：先确认方案，后展示 `assets/style-references/style-choice-1x4.png` 并确认风格。图中文字仅为宁海示例，不能被当成本次行程。不得直接跳到终稿。终稿固定为一张 1:5 PNG；中文正文以确定性排版为主，生图优先承担无字视觉。以确认版 `trip.json` 对照复核所有日期、时刻、地点、金额、预约和风险。长图不代替 MD/HTML 两份完整攻略。

旧版图片行程卡不再是默认交付；只有用户另行要求时才考虑额外卡片。行程变化后旧长图标记过期，不能与新版 MD/HTML 混用。无生图能力但可本地排版导出时继续完成；无法导出图片时明确说明长图未完成。

## 7. 存档、恢复与修改（S10）

### 7.1 目录与隐私

```text
travel-plan/<trip_id>/
  trip.json                 唯一业务数据源
  versions/trip.v<N>.json   已渲染或编辑前建立的不可变快照
  audit.v<N>.json           核查报告
  manifest.v<N>.json        产物清单
  outputs/                  MD / HTML / 1:5 PNG
  tikhub-usage.json          可选：跨命令累计的请求消费账本（无令牌）
```

- 首次创建时说明保存位置与内容，允许用户选择不保存。
- 令牌与长期偏好放在此目录**之外**；长期偏好另设开关，允许查看、修改、删除；身体、证件、同行人身份等敏感资料不默认入库。
- 默认不长期保留完整社媒原始响应、评论者个人信息、整页抓取副本；只留必要事实摘要、短摘录、原链接、时间。排查问题需要临时原始响应时先脱敏、限制保留范围、由明确清理动作处理；没有实际调度能力不承诺自动到期删除。
- **本地保存 ≠ 所有处理都在本地**：宿主模型、联网服务、TikHub 仍可能处理发送给它们的数据，只发送调研所需的最小信息。

### 7.2 版本与写入（`scripts/state_io.py`）

```bash
python scripts/state_io.py init <trip_id> --dir travel-plan
# 先复制 trip.json 为同目录 edited.json，在 edited.json 中修改；保留原文件
python scripts/state_io.py save travel-plan/<trip_id>/trip.json --from travel-plan/<trip_id>/edited.json --summary "改了第二天上午"
python scripts/state_io.py versions travel-plan/<trip_id>
python scripts/state_io.py diff travel-plan/<trip_id> 1 2
python scripts/state_io.py restore travel-plan/<trip_id> 1
python scripts/state_io.py scan travel-plan/<trip_id>
# 确实要原地编辑时，必须在编辑之前执行；已渲染版本自动有快照
python scripts/state_io.py checkpoint travel-plan/<trip_id>/trip.json
```

推荐候选文件方式：`edited.json` 与原数据保持相同 `trip_id` 和原 `plan_version`，由 `save --from` 自动升版本。没有旧快照时，编辑后才运行普通 `save` 无法找回原内容，因此会拒绝；不要在已经改坏的文件上补做 checkpoint 并称其为旧版。初始骨架 `days=[]`，日期未知时不填 1970 年等占位日期；空行程只允许草案。

`save` 清除核查时间和用户确认，状态回到草案；旅行日期变化还会使事实与行程项的核查状态失效。保存后完成必要重查、更新核查时间和状态，再渲染新版本；新版本渲染前仍可补齐这些字段。`restore` 保留当前版本和变更记录，以递增的新版本恢复旧内容，并清除过期核查状态。真实预订记录不会因为重新核查而被取消。

规则：原子写入（先写临时文件再替换）、不静默覆盖、`trip_id` 只允许 `[a-z0-9-]`、路径必须落在行程目录内、任何文件里不得有凭据。

### 7.3 修改按依赖关系，不重做整次旅行

用户修改某一天、预算、住宿、出发时间时：

1. **确认影响范围**，并锁定未改变的预订与已确认安排；
2. 在同目录候选文件 `edited.json` 中更新受影响的地点、路段、预算、预约与清单；
3. 相关 `FactRecord` 核查状态失效（改为 `unknown` 并注明原因）；
4. `state_io.py save --from` 生成新版本 → 重查受影响事实、更新核查时间与方案状态 → `validate_trip.py` → `render_outputs.py` → `--check-outputs`；
5. 变更摘要只说明改了什么、为什么、用户还需要做什么；同时重渲染 MD 与 HTML，提示旧长图已过期，重新走方案和风格确认；
6. 两个基础文件都成功后，才把新版本标为交付完成；旧版本保留便于回退，不覆盖用户已编辑的文件。

依赖链示例：住宿位置变化 → 当日首末路段变化 → 起床/出发时间变化 → 预约可达性重查。旅行日期变化通常影响全程的星期、开放、天气、预约 → 触发全量日期相关核查（T19）。

### 7.4 恢复

新对话里只能读取当前环境真实可访问的存档：先找 `travel-plan/<trip_id>/trip.json`；找不到就请用户重新提供已生成的 HTML 或 MD（HTML 内嵌了 `alun-trip-snapshot` 数据块，只解析数据、不执行脚本）；两者都没有就如实说明，⛔ 不假装拥有跨会话记忆（T22）。

## 8. 没有脚本能力时的模板路径

- 用 `assets/templates/itinerary.html` 的区域结构手工填写（占位符全部替换），所有外部文本手工转义 `< > & "`；
- MD 按 §3 的十个模块顺序写；
- 逐项人工复核 `audit.md` §2 的八个维度，并在交付说明与文件里写明"**自动校验未执行，已逐项人工复核**"；
- 署名、版本、日期照常写；
- ⛔ 不得声称脚本校验已通过。
